# 실패 상태 정확성 설계

**날짜:** 2026-07-12
**범위:** 과목 상태 변경 optimistic UI 롤백, 졸업요건 조회 오류 및 재시도 상태

## 문제

과목 상태 변경 요청은 Zustand의 `activePlan`을 먼저 바꾸지만, 요청 실패 시 실제 UI 상태를 복구하지 않고 React Query의 잘못된 상세 키만 무효화한다. 따라서 서버에는 반영되지 않은 상태가 화면에 남을 수 있다.

졸업요건 카드는 요구사항 및 진행률 쿼리의 오류를 읽지 않는다. 요구사항 조회 실패는 정상적인 미설정 상태처럼 보이고, 진행률 조회 실패는 기본 0 값으로 대체되어 0%처럼 보인다.

## 목표

- 과목 상태 변경 요청이 실패하면 해당 optimistic 변경을 요청 전 상태로 즉시 복구한다.
- 복구 후 현재 사용자 계획의 실제 쿼리 키를 stale로 표시하되 즉시 전체 plan을 다시 hydrate하지 않는다. 이후 안전한 일반 쿼리 lifecycle에서 서버 상태와 수렴시킨다.
- 졸업요건 또는 진행률 조회가 실패하면 수치나 미설정 상태를 표시하지 않는다.
- 오류 카드에서 사용자가 두 조회를 다시 시도할 수 있고, 재시도 진행 상태를 알 수 있다.
- 게스트 모드는 네트워크 요청을 하지 않는 기존 동작을 유지한다.

## 설계

### 과목 상태 롤백

`useUpdateCourseStatus`의 mutation lifecycle에서 요청 직전 해당 과목의 상태 값을 보존한 뒤 optimistic update를 적용한다. 실패하면 현재 plan에서 같은 과목을 찾아 그 상태 필드만 즉시 복구한다. 이렇게 하면 요청 대기 중 추가·삭제·이동된 다른 과목이나 학기 변경을 과거의 전체 plan 스냅샷이 덮어쓰지 않는다.

같은 과목의 상태 요청은 handler 내부의 과목별 queue로 직렬화한다. 뒤 요청의 `onMutate`는 앞 요청의 성공 또는 롤백이 끝난 뒤 이전 상태를 읽고 적용한다. 따라서 앞 요청과 뒤 요청이 모두 실패해도 최초 서버 상태까지 순서대로 복구되며, 먼저 시작한 실패가 나중 optimistic 상태를 덮어쓰지 않는다. 서로 다른 과목의 요청은 독립적으로 진행할 수 있다.

성공 또는 실패 후 `planKeys.detail('my')`를 `refetchType: 'none'`으로 무효화해 stale로만 표시한다. 즉시 GET 또는 반환된 전체 plan으로 cache를 교체하면 planner의 전체 hydration이 아직 대기 중인 다른 optimistic 변경을 지울 수 있기 때문이다. 이후 focus/mount 등 일반 쿼리 lifecycle이 stale plan을 다시 가져온다. 성공 시 졸업요건 진행률 키는 non-blocking으로 무효화해 이 별도 요청이 상태 queue 해제를 막지 않게 한다. 기존의 동적 `planId` 상세 키 무효화는 실제 화면이 구독하는 키가 아니므로 제거한다.

게스트 경로는 로컬 store 두 곳을 즉시 갱신하고 API mutation을 사용하지 않는 현재 동작을 유지한다.

### 졸업요건 오류와 재시도

`RequirementsSummary`는 요구사항 쿼리와 진행률 쿼리의 `isError`, `refetch`, `isFetching`을 함께 사용하고, 오류에서 시작한 재시도 여부를 로컬 latch로 보존한다. TanStack Query가 no-data 오류를 재시도할 때 잠시 `isError=false`, `isLoading=true`로 전환하더라도 이 latch가 오류 카드를 유지한다.

표시 우선순위는 다음과 같다.

1. 오류에서 시작한 재시도 중이면 오류 카드와 비활성화된 재시도 버튼을 유지한다.
2. 초기 조회 중이면 skeleton을 표시한다.
3. 어느 한 쿼리라도 실패하면 오류 카드만 표시한다.
4. 오류 없이 요구사항 또는 진행률 데이터가 아직 `undefined`이면 skeleton을 표시한다.
5. 두 쿼리가 성공했고 요구사항이 `null`이면 정상적인 미설정 카드를 표시한다.
6. 요구사항이 있고 진행률도 `undefined`가 아니면 진행률 카드를 표시한다.

오류 카드에는 “졸업요건 정보를 불러오지 못했습니다.”와 `다시 시도` 버튼을 표시한다. 버튼은 latch를 먼저 켠 뒤 두 쿼리를 함께 `refetch`하여 서로 다른 시점의 요구사항과 진행률이 섞이지 않게 한다. 두 요청이 모두 settle할 때까지 latch를 유지하고 `finally`에서 해제한다. 재시도 중에는 버튼을 비활성화하고 `다시 시도 중...`으로 표시한다. 재시도 실패 시 쿼리 오류 상태가 카드를 계속 유지하며, 예상 밖의 reject는 Sentry에 기록한다.

기존 데이터가 캐시에 남아 있더라도 쿼리가 오류 상태라면 정확성을 위해 수치 카드를 숨긴다. 오래된 성공 데이터를 현재 값처럼 보여주는 방식은 사용하지 않는다.

## 테스트

- mutation 실패 시 해당 과목 상태만 복구되고 요청 중 발생한 다른 plan 변경은 보존되는지 검증한다.
- 같은 과목의 겹친 요청이 순서대로 optimistic update와 rollback을 수행하는지 검증한다.
- 성공 또는 실패 후 `planKeys.detail('my')`가 immediate refetch 없이 stale 처리되어 다른 optimistic 변경을 보존하는지 검증한다.
- 졸업요건 진행률 갱신이 상태 queue 해제를 기다리게 하지 않는지 검증한다.
- 요구사항 조회 실패가 미설정 상태보다 오류 상태를 우선하는지 검증한다.
- 진행률 조회 실패가 0% fallback보다 오류 상태를 우선하는지 검증한다.
- `undefined` 요구사항 또는 진행률이 ready/0%로 분류되지 않는지 검증한다.
- 두 refetch가 함께 시작되고 성공·실패 모두에서 재시도 latch가 마지막에 정리되는지 검증한다.
- 오류 카드에 재시도 동작, 비활성화 상태, 재시도 중 문구가 연결되는지 검증한다.
- 전체 테스트, TypeScript, ESLint, production build, CRLF-aware diff check, `git push --dry-run origin main`을 통과해야 커밋·푸시 준비 완료로 판단한다.

## 범위 제외

- API route 또는 service의 응답 형식 변경
- 과목 상태 성공 UX 및 졸업요건 수치 계산 방식 변경
- 게스트 모드의 로컬 계산 방식 변경
- 실제 커밋 또는 원격 push
